# Dependency and CI Reproducibility Policy

## Goal

Repository Assurance maintains a deterministic CI dependency baseline without
pretending that a GitHub-hosted runner is a fully hermetic build environment.

The required CI lane fixes:

- runner family: ubuntu-24.04
- interpreter: CPython 3.12.14
- Python build, runtime, development, and plugin dependency versions:
  requirements/ci.lock
- dependency artifacts: SHA-256 hashes enforced by pip --require-hashes

The GitHub-hosted Ubuntu image itself can still receive image/tooling updates.
Therefore this policy promises a locked Python dependency baseline, not bit-for-bit
machine reproduction.

## Source of truth

pyproject.toml remains the project dependency contract and contains supported
version ranges.

requirements/ci.lock is a generated CI baseline. It includes:

- project runtime dependencies
- all project extras
- PEP 517 build-system requirements
- exact versions
- package hashes

The lock is generated by pip-tools==7.6.1 using CPython 3.12.

The required CI environment currently runs CPython 3.12.14. Lock regeneration
should use CPython 3.12, and release/CI changes that alter the pinned interpreter
must regenerate and verify the lock.

## Required CI installation

CI installs the locked dependency set first:

    python -m pip install --require-hashes -r requirements/ci.lock

It then installs the repository package itself without dependency resolution or an
isolated build environment:

    python -m pip install --no-deps --no-build-isolation -e .

This ensures the editable project is built using the build backend already present
in the locked dependency set.

## Compatibility testing

The lock is not the declaration of every dependency version the project supports.

Developers may intentionally install the declared ranges:

    python -m pip install -e '.[dev,plugin]'

That path is useful for compatibility testing. The required CI lane chooses the
locked baseline to make ordinary PR/test results reproducible across runs.

A future compatibility matrix may exercise minimum/latest supported dependency
ranges separately without weakening the locked required lane.

## Regenerating the CI lock

Use a clean CPython 3.12 environment:

    python3.12 -m venv .venv-lock
    . .venv-lock/bin/activate
    python -m pip install 'pip-tools==7.6.1'
    python scripts/update_ci_lock.py

The default command preserves compatible pins already present in the lock and is
also used by CI as a freshness check. To intentionally refresh dependency versions:

    python scripts/update_ci_lock.py --upgrade

Then:

1. review the requirements/ci.lock diff
2. verify expected direct and transitive dependency changes
3. install the lock with --require-hashes in a clean environment
4. install the project with --no-deps --no-build-isolation -e .
5. run the full test suite and plugin build
6. submit the lock update in the same PR as the dependency-range change that
   required it

The generator fails closed when run outside Python 3.12 or with a different
pip-tools version. `pip-tools==7.6.1` is itself part of the generated CI baseline,
so the required CI lane can verify that the committed lock still matches the
project metadata without introducing an unpinned lock-generation tool.

## Auditor semantics

Repository Assurance records dependency reproducibility as repository profile
evidence:

- LOCKED_BASELINE_OBSERVED: a recognized lock artifact is present
- CONSTRAINTS_BASELINE_OBSERVED: a recognized constraints baseline is present
- NOT_OBSERVED: neither is visible at the audited commit

These states are descriptive observations.

NOT_OBSERVED is not by itself:

- a vulnerability
- a supply-chain compromise
- proof of non-reproducibility for every project
- a canonical security finding

Different ecosystems and repository types legitimately use different dependency
management strategies. Security/vulnerability findings require separate evidence.

## Authoritative tooling basis

The lock generation workflow follows pip-tools support for compiling
pyproject.toml, including all extras/build dependencies and generated hashes.
